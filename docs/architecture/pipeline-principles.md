# Pipeline Principles

**Project:** Norsk Trainer

**Document version:** 1.0

---

# Цель

Language Processing Pipeline является единственным механизмом обработки языка в системе.

Он используется для:

- анализа нового текста;
- Reading Analyzer;
- Voice Analyzer;
- Dictionary Maintenance;
- Batch Refresh;
- Import Pipeline;
- будущих AI-модулей.

Независимо от источника данных всегда используется один и тот же Pipeline.

---

# Основные принципы

## 1. Single Responsibility

Каждый модуль отвечает только за одну задачу.

Пример:

Grammar Parser

↓

Expression Resolver

↓

Lexeme Resolver

↓

Lexeme360

↓

Verification

↓

Promotion

Никакой модуль не выполняет задачи соседнего.

---

## 2. Pipeline Orchestrator

Только

```
index.ts
```

определяет порядок выполнения.

Все остальные модули являются независимыми.

---

## 3. Expression First

Главное правило системы.

Всегда сначала анализируются выражения.

Только после этого анализируются отдельные слова.

Запрещено:

```
tar
med
```

если существует

```
ta med
```

---

## 4. Longest Match First

Parser всегда ищет самое длинное совпадение.

Например

```
gå ut fra
```

имеет больший приоритет чем

```
gå ut
```

---

## 5. Two-pass Parsing

Pipeline использует два прохода.

### Pass 1

Поиск известных выражений.

↓

Resolver.

↓

Lexeme360.

### Pass 2

Повторный анализ текста после обогащения.

Цель —

найти выражения,

которые появились благодаря Lexeme360.

Pipeline никогда не выполняет более двух проходов.

---

## 6. Idempotency

Любой этап можно выполнить повторно.

Повторный запуск не должен:

- создавать дубликаты;
- ухудшать данные;
- менять результат без причины.

---

## 7. Deterministic Processing

При одинаковом:

- тексте;
- версии Parser;
- версии базы;

Pipeline обязан вернуть одинаковый результат.

---

## 8. Stateless Modules

Модули не должны хранить внутреннее состояние.

Каждый этап получает только входные данные.

Каждый этап возвращает только результат.

---

## 9. Recoverability

Pipeline обязан продолжить работу после сбоя.

Job хранит:

- current_stage;
- stage_started_at;
- stage_finished_at;
- processed_count;
- total_count;
- last_error.

После сбоя Pipeline продолжает работу с последней завершённой стадии.

---

## 10. Versioned Knowledge

Словарь постоянно развивается.

Данные могут изменяться.

Например

```
candidate

↓

multi_source

↓

authoritative
```

Это считается нормальным процессом развития базы.

---

## 11. Historical Trace

Каждое изменение должно быть воспроизводимо.

Для каждого обновления сохраняется:

- parser_version;
- grammar_version;
- verification_version;
- promotion_version;
- semantic_version;
- translation_version;
- source_versions;
- changed_by_stage;
- changed_at;
- reason.

История изменений не удаляется.

---

## 12. Dictionary Refresh

Через некоторое время Pipeline может быть повторно запущен

для всей базы.

Причины:

- новая версия Parser;
- новые алгоритмы;
- новые источники;
- новые статьи в Ordbokene;
- новые статьи в NAOB;
- улучшение Verification.

Обновление базы считается нормальной операцией.

---

## 13. Knowledge Evolution

Слабые выражения могут становиться сильными.

Например

Version 1

```
candidate

Ordbokene sub_article
```

↓

Version 2

```
multi_source

Ordbokene article

NAOB
```

↓

Version 3

```
authoritative
```

Pipeline обязан поддерживать подобную эволюцию.

---

## 14. Auditability

Любое изменение должно отвечать на вопрос

> Почему это произошло?

Для каждой записи сохраняется:

- источник;
- evidence;
- версия алгоритма;
- причина изменения.

---

## 15. One Source of Truth

Для каждого типа данных существует один источник истины.

Например

Expression Catalog —

единственный источник известных выражений.

Временные таблицы не должны использоваться как постоянное хранилище.

---

## 16. Separation of Concerns

Parser понимает текст.

Resolver понимает словарь.

Verification понимает качество.

Promotion изменяет словарь.

Lexeme360 расширяет знания.

Ни один модуль не нарушает границы другого.

---

## 17. Performance

Pipeline должен сначала использовать:

1. локальную базу;

2. локальный Expression Catalog;

3. Lexeme360;

и только затем обращаться к внешним источникам.

Минимизируется количество сетевых запросов.

---

## 18. Future Compatibility

Добавление нового этапа Pipeline

не должно требовать изменения существующих модулей.

Новый модуль подключается только через Pipeline Orchestrator.

---

# Главная цель проекта

Создать саморазвивающийся словарь норвежского языка.

Каждый новый анализ текста должен:

- улучшать качество словаря;
- расширять словарь;
- уточнять существующие данные;
- никогда не разрушать архитектуру Pipeline.
