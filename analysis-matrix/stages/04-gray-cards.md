# 04 — Серые карточки

## Назначение
Пункт, остановленный у входной проверки, всё же получает карточку низкого уровня (ai_candidate), если это
клон части речи с подтверждением словаря, слово с несколькими статьями Ordbøkene одной части речи или
уже существующая карточка.

## Код
SQL `public.d10_promote_gray_pos_clones_v1(job)` [живой текст: база `20261020100000_d10_gray_no_downgrade_v1`
+ патчи `20261024100000` (привязка второй карточки по homograph_key), `20261110180000` / `20261110190000` (D1)].
Вызов: job-orchestrator, до шагов семейства и омонимов.

## Логика [проверено]
- Существующая карточка (lemma + pos) → пункт привязывается к ней (`promoted_gray`, gray_path existing_card /
  pos_clone / several_articles); карточка НЕ меняется (no downgrade).
- Новая карточка для клона — только если есть проверка Ordbokene / NAOB / Lexin c `found`, `pos_match='match'`,
  `registered_entry=true`; иначе пункт остаётся у входной проверки (`gray_skip_reason POS_NOT_CONFIRMED_BY_DICTIONARY`).
- Несколько статей Ordbøkene одной части речи → новая карточка; статью ей выдаёт шаг омонимов (07).
- Источник карточки: `pipeline_gray_pos_clone`, tier `ai_candidate`, status `candidate`.

## Повторный анализ
Существующая карточка никогда не меняется этим этапом (по правилу). [проверено]

## Известные проблемы
- stemme (сущ.) `f6aa73c6…` — старая карточка без привязки к статье Ordbøkene.
- NAOB «подтверждение» по списку поиска (`naob_search_listing`, registered=false) — не засчитывается с v2.
