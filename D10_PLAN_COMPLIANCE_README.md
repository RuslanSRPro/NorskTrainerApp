# D10 — приведение обогащения к плану (§2, §6), версия после ревью

## Что меняется

### 1. Supervisor: строгий контракт ответа обработчика

Новый модуль `_shared/d10-enrichment-page-contract.ts`, функция `evaluateEnrichmentPage`. Ответ обработчика:

- **ожидает остаток** — `residue_waiting > 0`. Цепочка остаётся на той же странице, повторяется только остаток.
- **страница готова** — `residue_waiting = 0`. Цепочка идёт дальше; `failed` записывается в отчёт.
- **неверный ответ** — во всех остальных случаях:
  - сетевая ошибка или падение обработчика;
  - поля остатка `null`, строкой, отрицательные, дробные или есть только одно из двух;
  - чужие `chain` или `offset`;
  - `has_more` без `next_offset` после этой страницы.

  Та же страница повторяется до 3 раз. Цепочка на неверном ответе никогда не продвигается.

Ответ без полей остатка принимается, только если это полный успех без отслеживаемых элементов: `ok = true` и `failed = 0`. Например, на странице нет элементов, которым нужна эта цепочка.

**Явное исключение из гарантии «задача минус ошибка».** Если страницу целиком нельзя загрузить или обработать 3 раза подряд, её нельзя разобрать по элементам. Такая страница пропускается и указывается в отчёте (`enrichment_skipped_pages`). Ошибки отдельных элементов сюда не попадают — см. п. 3.

### 2. Supervisor: удалён старый путь

Удалено: отложенный повтор страницы, дробление по одному элементу, повторный прогон цепочек. Снимок 67 показал, что незавершённых задач на этом пути нет.

### 3. Обработчик: ошибка одного элемента не губит пачку

- **Цепочки с вызовом на каждый элемент** (Ordbøkene, NAOB, переводы, authoritative). Ошибка одного вызова уже записывается только этому элементу.
- **Агрегатные цепочки** (AI fallback ×2, переупорядочивание и канонизация переводов, формы) отправляют остаток одной пачкой. Если такая пачка упала целиком без указания элемента, повторная пачка уменьшается:
  1. попытка 0 — весь остаток;
  2. попытка 1 — половина;
  3. последняя попытка — по одному элементу.

  Первыми идут элементы с наибольшим числом попыток. Пример: страница из 20, один «ядовитый» элемент. Он один получает `failed`, остальные 19 — `done`; невиновные успевают не более чем за 2 попытки. Поштучный режим — только последняя ступень (план §6).
- Для этого нужна новая функция `d10_enrichment_residue_attempts_v1` (только чтение, только для служебной роли).

### 4. Не меняется

- Журнал остатка.
- Цепочки с вызовом на каждый элемент.
- Проверка отсутствующих форм.
- Этапы orchestrator и аудита.
- Итоговый отчёт.
- Элемент с `failed` идёт в следующие цепочки (решение 12.10.2026).
- `item_ids` на входе обработчика не добавлен: остаток он отбирает сам по журналу.

## Установка

1. Распаковать архив в «Загрузки». Из корня проекта:

   ```powershell
   Expand-Archive -LiteralPath "$env:USERPROFILE\Downloads\D10_plan_compliance_v1.zip" -DestinationPath "$env:USERPROFILE\Downloads" -Force
   powershell -ExecutionPolicy Bypass -File "$env:USERPROFILE\Downloads\D10_plan_compliance_v1\install_d10_plan_compliance.ps1"
   ```

2. SQL Editor: `scripts/d10/67_d10_live_runtime_snapshot.sql`. Раздела `3_legacy_keys` и строк в `4_active_jobs` быть не должно (новые задачи на время установки не запускать).
3. SQL Editor: миграция `supabase/migrations/20261012200000_d10_enrichment_residue_attempts_v1.sql`.
4. SQL Editor: `scripts/d10/68_d10_residue_scenario_test.sql`. Ответом будет ошибка `D10_RESIDUE_SCENARIO_REPORT` — так тест всё откатывает. S1–S8 должны быть PASS.
5. Деплой, обработчик первым:

   ```powershell
   npx supabase functions deploy job-enrichment-batch-worker
   npx supabase functions deploy pipeline-supervisor
   ```

   Новый обработчик отвечает в прежнем формате, поэтому старый supervisor с ним работает. Новый supervisor требует только того, что старый обработчик уже отдаёт.

Откат: вернуть оба `index.ts` из `*.d10-plan-compliance.bak` и задеплоить обе функции. Новую SQL-функцию можно оставить.
